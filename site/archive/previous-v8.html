Heimdall: the self-hosted harness for AI code review

Open source · MIT · Runs in your CI or on your server · Any OpenAI-compatible model

Coding agents now write pull requests faster than people can read them. Heimdall puts AI review agents on every pull request, writes the CI tests your code is missing, and turns each finding into a test. Only a finding that a test proves can block the merge. A person approves the exact commit.

#1. What it does

Review at volume

Independent AI reviewers read every change. Heimdall also reads the comments of the bots you already use: CodeRabbit, Copilot, Bugbot, Greptile and Macroscope. Parsers

Real CI tests

In team mode, an agent writes tests from the ticket before the code exists. A test that passes without the feature is rejected. The rest are pinned and run in CI on every pull request. Evidence

Proof before merge

A finding counts only when its test fails twice on the pull request and passes on the fix. Unproven findings are hidden and counted. Plain Go rules decide the merge, never a model.

AI review bots leave many comments, and few of them change the code. We read every bot review comment on 30 merged pull requests of an active open-source repository, pingdotgg/t3code. There were 411 comments, a median of 10 per pull request.

#3. How it works

Heimdall uses one rule for every finding, its own and other bots'.

  1. Collect. Heimdall reads every review comment on the pull request, and its own reviewers add theirs.
  2. Prove. A finding needs a test that fails twice on the pull request and passes on the fixed tree. One red run is not proof, and a build error is not proof. The test runs in a sandbox with no network.
  3. Decide. A proven finding blocks the merge. Unproven ones are hidden and counted, and anyone can open the list. A person approves the exact commit.

Heimdall runs in one of two places. Both use the same rules.

#4. Set it up

GitHub Action mode needs no server and no database. You need admin rights on the repository, the gh CLI, Go 1.27, and a key for an OpenAI-compatible model endpoint. The CLI runs on Linux, macOS and Windows.

1. Build the CLI

git clone https://github.com/prathameshk421/Heimdall.git && cd Heimdall
CGO_ENABLED=0 go build -o heimdall ./cmd/heimdall

2. Read the plan

./heimdall action init -repo OWNER/REPO -dir PATH/TO/CHECKOUT

It lists every step and changes nothing.

3. Apply it

./heimdall action init -repo OWNER/REPO -dir PATH/TO/CHECKOUT \
  -apply -model-key-stdin < KEY_FILE

This creates a GitHub environment and the secrets, sets the model, and writes three workflows and a shadow-mode heimdall.yaml into your checkout. The workflows are pinned to the exact Heimdall commit you built. The key goes to gh on stdin and is never printed. On our test repository this step took 9 seconds.

4. Merge the files

Commit the workflows and heimdall.yaml through your normal review. Open any pull request: Heimdall posts heimdall/fast, heimdall/proof and one summary comment. Shadow mode blocks nothing and shows what would block. A full install reached its first summary in 3 minutes 10 seconds.

Another model, enforce mode and removal: the install guide. Team mode on your own server: the setup guide.

#5. Set it up with your coding agent

Heimdall ships a setup skill for coding agents such as Claude Code. The skill is inside the CLI, so one command installs it:

./heimdall skill install

Then ask your agent:

Set up Heimdall on OWNER/REPO.
It shows the plan first
The agent runs every init without -apply and shows you the steps before it changes anything.
It never sees your secrets
You keep each key in a file. The agent passes the file on stdin and never prints, pastes or commits a value.
It leaves the default branch to you
The agent writes the files on a branch and opens a pull request. You merge it.
It checks its work
It runs the checks, reads the pull request status, and ends with a list of what it could not verify.

For another agent, print the skill with ./heimdall skill, or install it into any folder with -dir. Read the skill.

#7. Built to be trusted

Heimdall runs pull request code, so the sandbox matters. On a GitHub-hosted runner, code under test tried to escape it 70 ways: 34 fetch and 36 exec probes. All 70 were blocked.

No model in the gate
A model may propose a finding. Only a test or a tool result decides. A missing fact is "unknown", never a pass.
Policy from the merge base
Heimdall reads heimdall.yaml at the merge base, so a pull request cannot change the rules that judge it.
A human approves the exact commit
An approval counts only from a person who is not the author, and only on the head commit.
Your model, your cap
Any OpenAI-compatible endpoint works, including a local one. Before every model call, Heimdall checks a worst-case cost bound against your per-PR and monthly cap.
A signed log
Each change has a log on one git ref, with an HMAC over each chain head. A bad MAC fails closed.

#9. Questions

Does it replace our AI reviewer?

No. Keep CodeRabbit, Copilot, Bugbot or any other bot. Heimdall checks their findings, and its own, with the same proof rule.

What if Heimdall is wrong?

Unproven means not shown, not false. A test can prove a bug is real, but never that a finding is false. Anyone can open the list of unproven findings and read them.

Will it block our merges on day one?

No. A new install runs in shadow mode: the checks say what would block and block nothing. heimdall action digest gives a weekly report. You switch to enforce mode when the report matches what your reviewers would say.

What about an emergency?

A named person posts a break-glass with a reason. It is recorded, and it shows as open until another approver reviews it. An agent cannot use it.

What does it cost to run?

Heimdall is free. You pay your own model provider. The default cap is $0.50 per pull request and $50 a month, and a call that could pass the cap does not run.

Where does our code go?

Nowhere new. Heimdall runs in your CI or on your server. Tests run with no network. Only the model endpoint you choose sees the code it reads.
